# 会话健康度评估（Session Health）

在长会话中评估「继续 vs 新开」的得失，判断是否该新开会话。**只评估不修改**任何会话文件。

核心原则：**压缩比例高 ≠ 该切换**；**窗口占比低 ≠ 经济无忧**。决策 = 继续成本（容量 + 质量 + 每轮 token 经济）vs 切换成本（丢失早期精确细节 + 交接轮次）的权衡。

## 何时使用

- **被动**：用户提到「压缩 / 新开会话 / 上下文开销 / context」时，立即完整评估。
- **主动**：长会话中用户持续推进（go / 继续 / 按计划推进）时，顺带检查一次；仅在**状态明显恶化或达到阈值**时提醒，否则一句「会话健康（压缩 x%）」带过。

## 硬约束

1. **只读评估**——不得修改 `~/.deepcode/projects/` 下任何文件（会话 JSONL / 索引 / 快照）。
2. **不夸大、不虚构**——数字来自实际文件统计；查不到就说明查不到，不猜。
3. **不机械建议切换**——必须评估工作性质与可恢复性；依赖早期内容的工作（重构/优化）即使压缩高也未必该切换。
4. **未达阈值不展开**——健康时一句话确认即可，完整报告只在达到阈值或用户要求时给。

## 数据获取（只读命令）

1. 定位当前项目会话目录（路径 → 目录名：`/` 替换为 `-`，如 `本地路径` → `-Volumes-NinjaSin-myself`）：

   ```bash
   ls -td ~/.deepcode/projects/*/ 2>/dev/null | head -3   # 找当前项目
   ```

2. 当前会话统计（消息数 + 压缩比例）：

   ```bash
   cd ~/.deepcode/projects/<project-code>
   LATEST=$(ls -t *.jsonl | head -1)
   TOTAL=$(wc -l < "$LATEST")
   COMPACTED=$(jq -r 'select(.compacted == true) | "x"' "$LATEST" 2>/dev/null | wc -l)
   echo "会话 $LATEST：$TOTAL 条，compacted $COMPACTED（$(( COMPACTED * 100 / TOTAL ))%）"
   ```

3. 活跃 token 开销（会话索引——token 用量 / 活跃 token 数）：

   ```bash
   jq -c '.[0] | {title, activeTokens, tokens}' ~/.deepcode/projects/<project-code>/sessions-index.json 2>/dev/null | head -1
   ```

   （若字段名不同，用 `jq 'keys'` 查看实际字段，不硬编码。）

4. 模型上下文窗口（判定活跃 token 比例用）：查 `references/model-contexts.md` 引用表（本技能目录下）。表内模型直接查；未收录 → 见「模型上下文引用表」节处理。查不到/过期 → 按该节刷新流程处理。

## 引用表（数据外置——稳定方法 vs 易变数据分层）

指向性/易变数据一律外置 `references/` 各表；SKILL.md 只留**稳定方法论**。每表自带 `lastUpdated` + `refreshInterval`（**按数据稳定性定**——上下文窗口 60 天 / 价格 30 天 / API ID 90 天 / CLI 行为 180 天），独立过期互不影响。

**使用规则**：
1. 需要外部数据（模型窗口 / 价格 / API ID 等）→ 查 `references/` 对应表；**表不存在** → 按同机制新建（含 lastUpdated + refreshInterval + 置信度列）
2. **未收录项**：询问用户提供（AskUserQuestion）或自行网络搜寻（优先官方/API 文档）→ 核实后入表（超上限按市场使用度淘汰）
3. **过期检查**：`lastUpdated` 距今 > `refreshInterval` → 使用前必须刷新：核实表内各项最新值 → 更新数值 + lastUpdated + 刷新记录；刷新失败项保留旧值并降置信度标注「待核实」
4. **计算示例**：活跃 token ÷ 查表窗口值——**窗口值一律查表，不在正文写死**（防双源）

**当前表**：
- `references/model-contexts.md`——模型上下文窗口（refreshInterval 60 天；市场前 15）

## 工作性质评估（切换成本——每次评估必答）

| # | 问题 | 回答为「是」→ 含义 |
|---|------|---------------------|
| 1a | 当前工作是否引用/修改**会话早期（压缩线以前）**的内容？（大型重构 / 优化 / 跨早期改动 = 是）| 依赖早期细节 → 切换丢失精确上下文 |
| 1b | （若 1a 是）依赖的早期**决策依据/命名约定/数字**是否已被 HANDOFF/git/文档记录？| **否 → 隐性上下文丢失，切换成本极高**（有代码无理由）|
| 2 | 早期相关改动是否已 **commit/push**？| **否 → 禁止切换**（未提交=切换丢工作成果）|
| 3 | HANDOFF / 项目文档是否记录了早期关键决策？| 是 → 可恢复性好（新会话可经 HANDOFF 找回）|
| 4 | 预计剩余工作量约多少轮对话？（1-2 轮 / 10-20 轮 / 数十轮）| 轮数多 → 继续会话的每轮历史输入费累积显著（切换省钱）|

- 切换成本 = 隐性上下文（#1b 否 → 极高）× 可恢复性（#2/#3 否 → 更高）× 任务中断（是否在任务边界——见「切换时点」）
- 独立新任务（#1a 否）→ 切换成本低
- **经济维度**（#4）：新开会话每轮输入 ≈ 只有新任务上下文（几 K token）；继续会话每轮输入 ≈ 活跃 token 绝对值（历史）——轮数多时差距累积
- **/resume 可恢复性**：同工具切换非冷启动——Deep Code `/resume` 可列出历史会话继续，恢复成本 ≈ 交接轮次（读 HANDOFF + 首轮上下文建立），非「从零重建」

## 判定：二维决策模型

### 维度 A —— 继续成本（容量 + 质量 + 经济）

| 信号 | 阈值 | 成本 |
|------|------|------|
| 活跃 token 窗口占比 | ≥ 50% 窗口 | 高（容量压力）|
| 活跃 token 窗口占比 | 30%–50% 窗口 | 中 |
| 活跃 token 窗口占比 | < 30% 窗口 | 低（容量充裕——大窗口下常如此）|
| 经济成本（绝对值 × 轮数）| 活跃 token ≥ 50K/轮 **且** 预计剩余 ≥10 轮 | 高（每轮历史输入费累积）|
| 经济成本 | 活跃 token ≥ 50K/轮 **或** 剩余 ≥10 轮 | 中 |
| 经济成本 | 其余（小历史 / 快收尾）| 低 |
| 压缩比例 | ≥ 50% | 中（早期细节概要化——**非容量危机**，git 可追溯）|
| 压缩比例 | 30%–50% | 低-中 |
| 消息数 | ≥ 800 条（代理指标，仅参考）| 低-中 |

多个信号取最严。**优先级**：经济成本（绝对值——与窗口无关，每轮都付）> 容量（窗口占比）> 压缩质量 > 消息数。

> 以上阈值为**默认参数**（按主流模型与成本结构校准）——可按项目实际调整。

> 窗口占比与绝对值的区别（以 deepseek-v4-flash 为例，窗口**查引用表**）：1M 窗口下 22 万活跃 token 占比仅 22%（容量健康），但每轮输入仍按 22 万 token 计费（经济成本——若剩余轮数多，切换显著省钱；若服务端有 context caching，历史部分可能折扣价，差距缩小但仍存在）。窗口值一律查表，不在正文写死。
>
> 估算口径：`activeTokens` 为会话索引**快照**；实际每轮输入 ≈ 压缩后的「摘要 + 未压缩消息」（可能小于快照）——经济评估用快照作上界估算，报告注明口径与方向（如「≤22 万/轮」）。

### 维度 B —— 切换成本（工作性质 + 可恢复性）

| 情形 | 切换成本 |
|------|----------|
| 独立新任务，早期改动已 commit | 低 |
| 依赖早期内容，但已 commit + HANDOFF 有记录 | 中（可恢复但需交接）|
| 依赖早期内容，且早期改动未提交 | 极高（**禁止切换**）|

### 结论矩阵

| A 继续成本 \ B 切换成本 | B 低（独立任务）| B 高（依赖早期内容）|
|------------------------|----------------|---------------------|
| **A 低**（健康）| 🟢 继续 | 🟢 **继续**（切换反而亏——用 git/JSONL 追溯早期细节）|
| **A 中** | 🟢 继续 | 🔵 继续，留意；如需切换先补交接（HANDOFF + commit）|
| **A 高** | 🟡 **建议切换**（交接收割）| 🔴 **危险区**：深度交接（HANDOFF 同步早期状态 + commit 后）再切换，或继续+git 追溯 |

## 切换时点建议（降低中断成本）

切换成本与「时点」强相关：

- **任务边界处切换最划算**：一个 commit / 阶段完成、无进行中的推理链 → 中断损失 ≈ 0，交接成本最低
- **任务中间切换最亏**：推理链进行中、半成品未落地 → 切换=打断思路 + 隐性状态丢失
- 主动触发时若处于任务中间：建议「先收尾（commit / 写 HANDOFF）再切换」，不裸切

## 输出格式

### 达到阈值时（🟡/🔴/🔵）

```
## 会话健康度评估

| 指标 | 当前值 | 判定 |
|------|--------|------|
| 压缩比例 | 65%（714/1100）| 🔵 概要化（非容量危机——git 可追溯）|
| 消息数 | 1100 条 | 🔵 代理指标 |
| 活跃 token | 221,648（窗口 22%——容量低 / 绝对值高）| 🟢 容量 / 🟡 经济 |

工作性质评估：
- 依赖早期内容？是/否（重构/优化说明）
- 早期改动已 commit？是/否（未提交 → 禁止切换）
- HANDOFF 记录？是/否
- 预计剩余轮数？N 轮（× 22 万/轮历史输入费 = 继续成本估算；新会话 ≈ 几 K/轮）
→ 切换成本：低/中/极高；经济结论：继续 / 切换省钱

**结论**：（按矩阵——建议切换 / 继续但留意 / 危险区需深度交接）

交接就绪检查（建议切换时）：
- [ ] git 工作树干净 / 未提交变更数
- [ ] 关键产出已 push（最新 commit hash）
- [ ] HANDOFF.md 存在且同步到最新
- [ ] 运行中进程？（dev server / LSP / 测试服务——切换前说明归属/清理）
- [ ] 会话内临时状态？（临时配置 / 未持久化改动——是否需记录）
- [ ] 测试状态（若项目有质量链）

新会话入口：输入「<项目名> 接手」走 project-intake 恢复上下文。
```

### 健康时（🟢）或切换反而亏时

> 会话健康（压缩 12%）——继续。
> 或：压缩 65% 但当前重构依赖早期 commit（已提交，可 git 追溯）——**切换反而亏，建议继续**。

## 交接就绪检查命令（建议新开会话时）

```bash
git status --short | head -5                     # 未提交变更
git log --oneline -1                              # 最新 commit
ls HANDOFF.md 2>/dev/null && echo "HANDOFF 存在"  # 交接文档
```

检查失败项（如未提交变更）→ 提醒先提交或说明不切换。

## 反模式

- 修改/删除 `~/.deepcode/projects/` 下的会话文件（只读评估）
- 不看实际数字就凭「感觉很长」建议新开会话
- 不看工作性质机械建议切换（重构依赖早期内容时切换反而亏）
- 只看窗口占比忽略绝对值（1M 窗口下 22% 容量健康 ≠ 每轮 22 万 token 免费）
- 剩余 1-2 轮仍建议切换（交接本身 1-2 轮成本，省不下）
- 早期改动未提交 git 仍建议切换（丢工作成果）
- 任务中间裸切（推理链进行中——先收尾再切）
- 忽略运行中进程/临时状态就建议切换（dev/LSP/test 归属不明）
- 建议新开会话却不给交接就绪检查（让用户裸切换）
- 虚构 token 数 / 窗口大小（查不到就说「索引无该字段」或注明估计）
- 把 activeTokens 快照当精确每轮成本（应注明「≤上界」口径）

## 完成标准

- [ ] 只读：未修改任何会话/索引/快照文件
- [ ] 数字来自实际文件统计（wc/jq），非估算
- [ ] 工作性质 5 问必答（依赖度 1a/记录完整性 1b/提交状态/HANDOFF/剩余轮数）——切换成本与经济有依据
- [ ] 结论按二维矩阵给出（继续成本 × 切换成本），非机械阈值
- [ ] 经济评估：窗口占比（容量）与绝对值（每轮成本）分别判；注明快照口径（≤上界）
- [ ] 切换建议含时点判断（任务边界 vs 任务中间——是否需先收尾）
- [ ] 达到阈值时含交接就绪检查（含进程/临时状态）；健康或切换反而亏时说明理由
- [ ] 新会话入口指引明确（project-intake / /resume 触发词）
