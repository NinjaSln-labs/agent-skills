# 各生态版本约定对照

> 用途：给 `version-management` 提供「同一套版本语义在不同生态里长什么样」的落地细节。
> 原则：**版本号语义以对外承诺为准，不以某生态的历史习惯为准**；跨生态发布要显式翻译。

## 一览表

| 生态 | 规范形态 | 排序/比较特点 | 依赖范围写法 | 不可变性与撤回 |
|---|---|---|---|---|
| npm / Cargo | SemVer `X.Y.Z[-pre][+build]` | 严格 SemVer 优先级 | `^1.2.3`（≥1.2.3 <2.0.0）、`~1.2.3`（<1.3.0）、`1.x`、`*` | npm 允许 72h 内 unpublish（曾致 left-pad 事件之后收紧）；`npm deprecate` 是标记 |
| Python（PEP 440） | `[N!]N(.N)*[{a\|b\|rc}N][.postN][.devN][+local]` | 见下方排序链 | `~=1.4.5`（兼容发布）、`==`、`!=`、`<=`、`<`、`===` | PyPI `yank`（PEP 592）：标记而非删除，安装器默认跳过 |
| Go modules | SemVer，且 **v2+ 必须写进模块路径** `example.com/m/v2` | 主版本是模块身份的一部分 | `require` 直接写版本；MVS 选最低可行版本 | 模块不可变 + checksum 数据库（sumdb）；`retract` 指令可声明撤回 |
| Maven | 自由字符串（`1.2.3`, `1.2.3-SNAPSHOT`），**不保证 SemVer** | 自有比较算法，与 SemVer 不完全一致 | `[1.0,2.0)`、`[1.0,)`、`1.+` | Maven Central **几乎完全不可撤回**（不删不改已发布构件） |
| NuGet / .NET | 版本号历史为四段；包版本用 SemVer 2 | 见下方「.NET 三个版本」 | `[1.0,2.0)`、`1.0.*`（浮动） | nuget.org 支持 unlist（不再列出，但仍可精确还原） |
| Android | `versionCode`（整数）+ `versionName`（字符串） | 商店只看 versionCode 的单调递增 | 不适用 | 已上传的 versionCode 不可复用 |
| Apple | `CFBundleShortVersionString` + `CFBundleVersion` | 构建号（CFBundleVersion）每次上传必须递增 | 不适用 | 已上传构建号不可复用 |
| OCI 镜像 | tag（可读别名）+ digest（内容地址） | digest 才是身份 | 按 digest 固定：`image@sha256:…` | tag **可变**；digest 天然不可变 |
| Kubernetes API | 版本**按 API group 独立**：`v1alpha1`/`v1beta1`/`v1` | 稳定级别决定生命周期 | 由 API 版本而非制品版本表达 | 已持久化的 API 版本不可移除，只能停服 / 转换 |
| Stripe API | 日期版本 `YYYY-MM-DD`（如 `2026-08-26.dahlia`） | 账号**创建时钉住**版本 | 请求头指定版本 | 旧版本长期保留；每月发布向后兼容，沿用上次主版名 |

## 关键细节

### npm / Cargo：0.x 的范围语义

- `^0.2.3` → `>=0.2.3 <0.3.0`（**不是** `<1.0.0`）——0.x 的 caret 只锁 minor。
- `^0.0.3` → 仅 `0.0.3`。这就是 `0.y.z` 被视作「不稳定」在工具层的具体后果。
- 发布 0.x 库意味着**接受**使用者会收到破坏性升级；要么尽快到 1.0.0，要么在 CHANGELOG 里把每次破坏写清楚。

### Python：PEP 440 排序与翻译

排序（低 → 高）：

```
.devN  <  aN (alpha)  <  bN (beta)  <  rcN  <  <正式发布>  <  .postN
```

- `X.Y` 与 `X.Y.0` 视为**同一个**发布（比较时补零）。
- **epoch**（`1!1.0`）用于「换版本体系但排序不能倒退」——从日期版切到 SemVer 的标准解法（一生只该用一次）。
- **local version**（`1.0+ubuntu.1`）表示下游补丁重建；PyPI **不允许**上传带 local 段的公开版本。
- SemVer 的 `-`/`+` **不能**出现在 Python 公开版本位；需要翻译（预发布用 `rc1`，构建信息进 local 段或元数据）。
- 库**不要**用 `==1.2.3` 精确锁（会挡住安全修复）；`==` 留给应用部署的可重现锁定。

### Go：主版本进路径

- 破坏性升级**必须**改模块路径（`/v2`），否则视为同一模块 → 这是把「MAJOR 是不同东西」编码进了 import 路径。
- 未打 tag 时工具生成**伪版本**（`v0.0.0-20170915032832-14c0d48ead0c`）——**不要手写**。
- `+incompatible`：模块化之前的仓库被打了 v2+ 的 tag，但没走 `/v2` 路径时出现，属历史包袱标记。
- 校验和数据库 = 内容不可变的外部强制力。

### .NET：三个版本各司其职（最容易被混淆）

| 属性 | 用途 | 变动频率 |
|---|---|---|
| `AssemblyVersion` | 运行时绑定标识、强名称 | **极保守**，通常只在破坏性变更时动大版本 |
| `FileVersion` | Windows 文件属性里的构建版本 | 随每次发布 |
| `InformationalVersion` | 自由字符串，承载 SCM 信息（配合 SourceLink） | 每次构建 |

发布用 `PackageVersion`（包语义版本）。**不要**让三者互相冒充——绑定标识被高频改动会造成引用错乱。

### 移动端：面向用户的号 vs 面向商店的号

- Android：`versionCode`（整数、单调、商店比较依据）／`versionName`（用户可见字符串）。
- Apple：`CFBundleVersion`（构建号，每次上传必须递增）／`CFBundleShortVersionString`（用户可见版本）。
- 共同规则：**用户可见号按发布节奏走，构建号每次上传都涨**；已用过的构建号不可复用。

### 容器镜像：tag 不是版本

- tag 是**可变指针**：同一个 `:1.2.3` 在不同时间可能指向不同 digest。把它当版本真相是供应链常见错误。
- 生产按 **digest** 固定（`image@sha256:…`）；tag 仅作人类可读别名。
- `latest` 不是版本号——它只是「最近一次 push」。
- 可复现构建 = 钉 digest；需要升级时**显式改 digest**。

### API 版本化 ≠ 制品版本化

两种成熟范式：

- **Stripe 式**：日期版本、账号创建时**钉住**、每月发布向后兼容、旧版本长期保留；URL 里的 `/v1` 只是稳定入口，真正的版本在请求头。
- **Kubernetes 式**：版本属于 **API group**，`alpha`（可随时移除）→ `beta`（弃用后约 3 个次版本/9 个月）→ `GA`（主版本内不移除）；元素只能**通过提升 API 版本**来移除。

要点：对外契约的版本（API 版本）与制品的版本（包/发布版本）**可以是两条平行的号**，别强行用一个号表达两种承诺。

## 跨生态发布的自检

- [ ] 该生态是否有**强制**的版本格式（Go 的路径主版本、PEP 440 的公开版本位）？
- [ ] 排序语义是否与我打算表达的兼容性一致（Maven/NuGet 的历史排序 ≠ SemVer）？
- [ ] 依赖范围写法是否会意外放行或拦住升级（caret/tilde/`~=`/浮动）？
- [ ] 该生态的撤回能力有多弱（Maven Central 几乎不可撤回）→ 发布前自检等级要提高
- [ ] 需要翻译时，**原始版本**存元数据、**公开版本**放可排序形式（PEP 440 的推荐做法）
